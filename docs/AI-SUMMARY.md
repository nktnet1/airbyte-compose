# AI Summary

This project reconstructs the supplied Airbyte Helm chart as a Docker Compose deployment. It does not call `abctl`, install the Helm chart, or hide the Airbyte control plane inside a Kubernetes deployment.

The Compose services are PostgreSQL, MinIO, Temporal, bootloader, server/UI, worker, cron, manifest server, workload API server, and workload launcher. Airbyte's workload launcher only runs connectors as Kubernetes pods, so the project also starts one lightweight K3s service for dynamically created check, discover, and sync workloads. Kubernetes service endpoints bridge those workload pods back to the explicit Compose services. A one-shot credentials bridge transfers the data-plane identity generated by bootloader to the Compose workload launcher without exposing it in `.env`.

## Requirements

- Docker Engine 24+ with Docker Compose v2
- At least 4 CPU cores, 8 GB RAM, and 30 GB free disk space
- Linux containers and permission to run a privileged container (required by K3s)
- Internet access to Docker Hub and Airbyte's connector registry

Docker Desktop users should allocate at least 8 GB RAM to Docker.

## Start Airbyte

Review `.env` first. It contains generated local credentials and all pinned image versions.

```sh
docker compose pull
docker compose up -d
docker compose ps
```

Open <http://localhost:8000>. The initial password is the `AIRBYTE_ADMIN_PASSWORD` value in `.env`.

The initial image pulls include K3s, the Airbyte platform, and Kubernetes system images, so the first start can take several minutes.

## Useful commands

```sh
# Follow the platform startup
docker compose logs -f bootloader server worker workload-launcher

# Inspect connector workload pods
docker compose exec k3s /bin/kubectl get pods -A

# Stop without deleting data
docker compose down

# Stop and delete PostgreSQL, MinIO, K3s state, and the generated kubeconfig
docker compose down --volumes
```

## Configuration notes

- The UI and API are bound to `127.0.0.1` only. Change the `server.ports` entry if remote access is intentional, and put a TLS reverse proxy in front of Airbyte.
- `.env` contains the settings normally changed by an operator. `config/airbyte.env` contains chart-derived non-secret application settings.
- The standard connector-definition update job remains enabled. The separate declarative-source image updater is disabled because its anonymous Docker Hub tag request can be rejected with HTTP 403; set `RUN_DECLARATIVE_SOURCES_UPDATER=true` only when that API is accessible from the cron container.
- Kubernetes CoreDNS forwards unresolved names to a DNS relay sharing the K3s container's Docker network namespace, so connector pods can resolve Compose services without a fixed Docker subnet.
- PostgreSQL and MinIO data use named volumes. Connector workload pods use K3s/containerd and are removed by Airbyte when jobs finish.
- Airbyte, Temporal, MinIO, manifest-server, and K3s versions are explicit tags in `.env`; no digest or floating `latest` tag is used.
- Authentication cookies are set for local HTTP (`AB_COOKIE_SECURE=false`). Enable secure cookies when serving the site through HTTPS.

## What was intentionally not included

The supplied chart disables the legacy standalone webapp, Keycloak, Temporal UI, metrics, Stigg, feature-flag server, and connector rollout worker. Airbyte serves the web interface from `airbyte/server`, so `http://localhost:8000` maps directly to that service.
